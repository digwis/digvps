# 远程项目管理改造设计

## 背景

当前项目中的“项目部署”页面以本地项目库为中心，围绕本地导入、项目脚手架生成、初始化和部署展开。这与新的产品目标不一致。

新的目标是把该页面改造成“项目管理”页面，以当前选中的 VPS 为中心，自动扫描远程服务器中由 Nginx 反向代理对外提供服务的网站项目，让用户进入页面后即可看到服务器上现有项目、域名、代理目标和推断出的项目目录。

## 目标

1. 移除“内容管理”页面及相关入口。
2. 将“项目部署”重命名为“项目管理”。
3. 去掉“创建平台项目”和“导入本地项目”能力。
4. 项目列表不再来自本地数据库中的 `local_projects`，而是来自当前 VPS 的实时扫描结果。
5. 以 Nginx 反向代理站点为主，自动展示远程项目的域名、配置文件、代理目标和项目路径。
6. 当无法直接识别路径时，继续通过 `systemd`、`pm2`、`docker` 等信息反推项目目录。

## 非目标

1. 本次不保留本地项目脚手架、导入、本地预览、本地启动等工作流。
2. 本次不尝试覆盖纯静态站点扫描。
3. 本次不实现完整的网站类型识别平台，只聚焦“由 Nginx 反向代理出去的网站项目”。
4. 本次不删除数据库表结构或做破坏性迁移，避免影响已有用户数据；未使用数据允许暂时保留。

## 用户结果

用户选择一台 VPS 后进入“项目管理”页面，应立即看到：

1. 这台服务器上有哪些由 Nginx 反向代理出去的网站项目。
2. 每个项目对应的域名或站点标识。
3. Nginx 配置文件位置。
4. `proxy_pass` 指向的目标地址或端口。
5. 推断出的项目目录。
6. 项目目录的推断来源，例如 `systemd`、`pm2`、`docker`、`heuristic` 或 `unknown`。

## 方案选择

采用“中度重构”方案。

理由如下：

1. 现有代码中已经有大量可复用的 SSH、远程执行、远程文件浏览、站点配置读取能力。
2. 现有“本地项目驱动”的产品心智必须替换掉，但不需要推翻整个远程管理基础设施。
3. 通过重构数据源和页面结构，可以较低成本实现“远程自动发现项目”的新模型。

## 信息架构调整

### 导航

1. 移除 `内容管理` 导航项。
2. 移除 `cms` 页面分支与相关入口。
3. 将 `项目部署` 文案统一替换为 `项目管理`。

### 项目管理页

1. 页面顶部保留“刷新扫描”之类的主动刷新入口。
2. 页面主内容改为“远程扫描项目列表”。
3. 移除以下入口和弹窗：
   - 创建平台项目
   - 导入本地项目
   - 与本地项目脚手架直接相关的配置表单
4. 项目卡片重点展示：
   - 域名
   - 项目路径
   - Nginx 配置文件
   - 代理目标
   - 推断来源
   - 状态摘要

## 数据来源与扫描规则

### 一级来源：Nginx 配置

扫描以下常见位置：

1. `/etc/nginx/conf.d/*.conf`
2. `/etc/nginx/sites-enabled/*`
3. `/etc/nginx/sites-available/*`

从配置中提取：

1. `server_name`
2. 配置文件绝对路径
3. `proxy_pass` 目标
4. 可选的监听端口、站点注释等补充信息

只保留存在 `proxy_pass` 的站点，作为“反向代理项目”候选项。

### 二级来源：路径推断

当候选项已识别出 `proxy_pass` 后，尝试按以下顺序推断项目目录：

1. `systemd`
   - 如果 `proxy_pass` 指向本机端口，优先查找监听该端口的进程，再关联对应服务。
   - 读取服务定义中的 `WorkingDirectory`、`ExecStart` 等信息。
2. `pm2`
   - 查询 pm2 进程列表与详情。
   - 读取 `cwd`、脚本路径、启动命令。
3. `docker` / `docker compose`
   - 查询容器端口映射。
   - 读取容器工作目录、挂载卷、compose 项目目录等信息。
4. 常见目录启发式探测
   - 如 `/var/www`、`/srv/www`、`/opt`、`/home/<user>`。
   - 结合域名、服务名、目录名做有限探测，避免广度过大。

如果多种来源都能得到路径，按可信度选择：

1. `systemd`
2. `pm2`
3. `docker`
4. `heuristic`

如果仍无法识别，则项目仍然显示，但路径标记为“未识别”，来源为 `unknown`。

## 数据模型

新增一个面向远程扫描结果的模型，替代本地项目列表在页面中的主地位。

建议结构：

```ts
type RemoteManagedProject = {
  id: string
  connectionId: string
  domain: string
  nginxConfigPath: string
  proxyTarget: string
  projectPath?: string
  pathSource: "systemd" | "pm2" | "docker" | "heuristic" | "unknown"
  serviceName?: string
  runtimeType?: "node" | "pm2" | "docker" | "unknown"
  status: "ok" | "warning" | "unknown"
  statusText: string
}
```

说明：

1. 该模型是“扫描态数据”，不是“登记态数据”。
2. 默认不写入数据库，优先通过 IPC 实时获取。
3. 允许后续再决定是否加入缓存层。

## 架构改造

### 主进程

新增“远程项目扫描”服务与 IPC：

1. 新增服务，例如 `remote-managed-projects.ts`
2. 负责：
   - 扫描 Nginx 配置
   - 解析 `server_name` 与 `proxy_pass`
   - 反查端口对应进程
   - 联动 `systemd` / `pm2` / `docker` 推断目录
3. 在 IPC 中新增类似 `scanRemoteProjects(connectionId)` 的入口

### 渲染层

1. 将 `project-store.ts` 从“本地项目 store”调整为“远程扫描项目 store”，或拆出新的远程项目 store。
2. `project-management-panel.tsx` 只消费远程扫描结果。
3. 页面依赖“当前选中的 VPS”，而不是“本地项目清单”。

### 复用能力

继续复用以下现有能力：

1. SSH 与远程执行链路
2. 远程文件浏览
3. 已有部分远程站点详情读取逻辑

删除或下线以下能力在页面中的入口：

1. 本地项目导入
2. 本地项目脚手架
3. 本地项目初始化
4. 本地项目一键部署
5. 本地开发预览相关入口

## 界面行为

### 默认状态

1. 未选择服务器时，提示先选择 VPS。
2. 已选择服务器但尚未扫描时，自动触发一次扫描。
3. 扫描中展示加载状态。
4. 扫描完成后展示项目卡片列表。

### 项目卡片

每张卡片展示：

1. 主域名
2. 项目路径
3. Nginx 配置路径
4. 代理目标
5. 推断来源
6. 状态摘要

可保留的动作：

1. 打开远程目录
2. 查看远程文件
3. 刷新该项目详情

不再保留的动作：

1. 创建平台项目
2. 导入本地项目
3. 本地启动
4. 本地部署

## 错误处理

1. 如果目标服务器未安装 Nginx，页面提示“未检测到 Nginx 反向代理项目”。
2. 如果 Nginx 存在但没有匹配的 `proxy_pass` 站点，展示空状态。
3. 如果扫描过程中某个站点无法识别路径，不阻断整体结果；该项目以“路径未识别”形式展示。
4. 如果 SSH 执行失败，则展示明确错误并允许重新扫描。

## 测试策略

新增或调整测试，聚焦高价值部分：

1. Nginx 配置解析测试
2. `proxy_pass` 提取测试
3. 项目路径来源优先级测试
4. 无路径时仍返回项目结果的测试
5. 导航与页面文案变更后的基础渲染测试

不为被删除的本地项目流程新增测试。

## 迁移策略

1. 先替换页面入口和数据来源。
2. 再下线本地项目操作按钮与弹窗。
3. 尽量不在本次删除底层数据库表，避免扩大风险。
4. 与 `cms` 相关的页面入口直接移除；保留未使用代码是否继续清理，视实现复杂度决定，但用户界面中不得再出现。

## 风险与约束

1. Nginx 配置风格可能高度定制，解析必须尽量容错。
2. 端口到项目路径的反推不可能百分百准确，因此 UI 必须允许“未识别”结果存在。
3. 部分项目可能跑在容器或进程管理器后面，必须允许多来源联合推断。
4. 现有 `project-management-panel.tsx` 文件职责较重，实现时可顺手做针对性的职责收敛，但不做无关重构。

## 实施清单

1. 移除 `cms` 导航和入口。
2. 将“项目部署”改名为“项目管理”。
3. 新增远程项目扫描服务和 IPC。

5. 将项目管理页切换到实时扫描结果。
